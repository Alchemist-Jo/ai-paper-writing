# Humanizer 与去 AI 味检查表

本文件将既有 Humanizer 规则收敛到 the user 的技术写作工作流。规则来源包括本机历史 Humanizer v2.8.0、MIT 许可的 [blader/humanizer](https://github.com/blader/humanizer) 和 [op7418/Humanizer-zh](https://github.com/op7418/Humanizer-zh)，并结合本机 `paper-polish` 的 AI-tone guardrails。这里只保留适用于技术和研究写作的行为规则，不复制旧 Skill 的平台配置或脚本。

## 上位原则

1. 重写问题片段，不删除原文承担的信息。
2. 保持作者含义、事实、数字、段落职责和不确定性。
3. 有作者样本时，匹配其句长、词汇、段落起点、标点和连接方式。
4. 技术报告保持中性、直接。博客和教程可以有叙事与节奏，但不得添加事实。
5. 去掉 AI 痕迹后仍要有逻辑和声音，不能得到均匀、空洞、无主次的文本。

## 内容模式

- 删除没有证据的宏大意义、时代趋势、历史转折和“奠定基础”。改写为具体对象、动作和结果。
- 删除宣传语言，如“突破性”“充满活力”“无缝”“直观且强大”。用功能、数据或行为替代。
- 删除无来源的“专家认为”“行业报告显示”“观察者指出”。给出具体来源，或删除归因。
- 删除句尾用来制造深度的空泛分析，如英文 `highlighting`、`underscoring`、`showcasing`。改成完整因果句，或删除。
- 不自动添加“挑战与未来展望”式模板章节。只有真实问题和证据时才写。
- 不把相关性改写成因果关系，不用推测填补“原因未查明”。
- 发布态正文删除 `notebook`、调试记录、生成脚本、内部文件名和“当前实现”等生产过程残留；只有影响证据边界时，才改写为读者可理解的“受控实验”“当前设定”或“配套实现”。

## 语言模式

- 避免高频 AI 词和空泛大词：`至关重要`、`深入探讨`、`复杂而深刻`、`格局`、`关键作用`、`展示`、`赋能`、`奠定基础`、`值得注意的是`。
- 简单系词足够时，不写“作为”“标志着”“代表着”“体现了……的重要性”。
- 不使用 `不仅……而且……`、`不只是……而是……`、`是 X，不是 Y` 等机械否定排比。证据模式无例外；解释模式仅在两侧对比都具有技术必要性时保留一次。
- 不强行把内容组织成三点，不为节奏补齐不存在的第三项。
- 同一对象保持一个名称，避免同义词循环。
- 不写两个端点不在同一尺度上的“从 X 到 Y”。
- 主体明确时优先主动句。不要用无主语片段隐藏操作者或责任边界。
- 删除聊天残留：`当然`、`好问题`、`希望这对你有帮助`、知识截止声明、谄媚和通用积极结尾。
- 删除重复限定和填充：`为了能够`、`在某种程度上可能也许`、`需要指出的是`。

## 版式模式

- 禁用 em dash `—` 和 en dash `–`，改用句号、逗号、冒号或拆句。
- 不机械加粗每个术语，不使用“粗体短标题 + 冒号”的连续竖排列表。
- 不添加装饰性 emoji、标题式大写或弯引号。
- 避免一个标题下面只有一句重复标题内容。

## 保留人的声音

- 句长可以变化，但变化服务内容，不刻意制造凌乱。
- 有真实权衡时直接写权衡，有不确定性时准确写不确定性。
- 教程和博客可保留“我们”以及作者已有的具体场景。
- 用准确事实、例子和限制产生声音，不用夸张形容词或无来源观点。
- 不把技术文本改成营销文案，也不把教程改成无声的百科条目。

## 最终扫描

1. 是否仍有宏大意义、宣传词、模糊归因或空泛总结？
2. 是否仍有机械否定排比、强制三段式、同义词循环或虚假范围？
3. 是否仍有 em dash、机械粗体、内联标题列表、emoji 或聊天残留？
4. 是否保留全部事实、数值、公式、限制和段落职责？
5. 技术报告是否保持中性？教程和博客是否保留作者已有声音？
6. 哪一句仍然明显像机器生成？指出原因后再改写。
